# Phase 4 alerting

Existing destination: repository GitHub Actions failure issues created by the existing bot workflow, plus provider dashboards and structured Render/Worker logs. No Slack/email/webhook destination or credentials were invented. Existing notification subscriptions were not changed.

| Condition | Severity / trigger window | Destination and suppression | Recovery / operator action |
| --- | --- | --- | --- |
| Backend/frontend/market/JWKS unavailable | Critical after bounded existing probe attempts; six-hour schedule | Existing Actions failure issue; one open bot issue per workflow, unchanged failures no longer update/renotify | Successful latest main run closes issue; inspect backend/auth runbook |
| Wrong live SHA/schema | Critical on independent release check | Same existing health workflow/issue; source SHA is not deployment evidence | Matching live metadata clears; inspect both providers |
| API errors/latency | Critical >5%/100 warm requests; warning p95 beyond1s market/2.5s data+identity/5s Engine in five buckets | Existing runtime log timer; transition state,15min cooldown, explicit unavailable for sparse traffic | Clear transition, including after cooldown; no user/action mutation |
| Pool/database/auth/Paystack dependency failures | Warning/critical >5%/20 measured operations | Same local transitions; auth expected4xx excluded | Dependency restored and sufficient measured samples |
| Neon quota | Warning70%, critical90% of dated allowance; critical actual hard suspension | Operator provider receipt -> capacity-report.mjs; no automatic quota fetch configured | Fresh same-period receipt clears; unavailable after26h; validate allowance rather than SQL byte guesses |
| Unusual transfer growth | Warning interval slope >10% monthly allowance/day, >=1h apart and same billing period | Operator dated receipt; no repeated sampling SQL | Inspect repeated query fingerprints/cache/job receipts; two points are not a reliable monthly forecast |
| Ingestion failed/missing/freshness | Critical failed scheduled run; warning >24h job age, expired lease or retry exhaustion | Existing independent GitHub receipts plus explicit private aggregate; no new poll | Successful run/checkpoint and source evidence current; missing expected publication date is unknown |
| Payment delay/unknown/review | Review count>0, age>1h, expired lease; maintenance>2h overdue | Phase3 persisted transitions only when separately approved flag/DDL active | Original-reference GET verification and fenced completion; disabled metrics unavailable |
| Failed deployment | Critical failed Cloudflare/Render build or revision skew | Provider-native dashboard and existing GitHub checks; health drift issue on next independent run | Known-good artifact, matching health and owner-read smoke; no automatic DB rollback |
| Security anomaly | Repeated auth/admission failures or new CodeQL/Dependabot issue | Existing security Actions/provider logs; no personal labels | Verify checks and authority boundary; never relax authentication to clear an alert |

alertPolicy.js is a pure aggregate evaluator; createAlertTransitions injects persistence and notification. Tests cover crossing, unchanged suppression, cooldown, clear/recovery, failed notification and provider-unavailable states. A failed delivery is retained for the next scheduled observation with a five-minute retry-after, not a retry loop. Current runtime wiring persists only in process memory, so restart may emit one initial observation; GitHub issues and Phase3 alert state provide durable suppression for their existing scopes. Persisting general runtime alert state or sending alerts to a new external destination needs approved configuration; it was not silently enabled.

The existing independent six-hour Actions health check remains outside sleeping Render; Phase4 adds a pinned JWKS read and revision reads, not a new schedule. It is a coarse safety net, not adequate detection for a fifteen-minute RPO. GitHub schedules can be delayed; a missing schedule must be reviewed through last-run receipts/provider UI. Workflow activation/cadence changes and notification subscriptions remain separately approved. Deployment failure detection is not claimed instant without configured provider notifications.
