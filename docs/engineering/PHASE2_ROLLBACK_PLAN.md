# Phase 2 rollback plan

Roll back application code independently of SQL. Pin the known-good Phase 1 eaf268c release for Render and Cloudflare, confirm health/live revision and managed Auth URL, and preserve collected diagnostics. Use normal deployments; do not force-push history or restore customer tables to roll back application code. A coordinated frontend rollback avoids sending new-only requests to an old backend.

Do not remove watchlist constraints merely because application code is reverted: the Phase 1 application is compatible with stricter ownership/default invariants, though old concurrent callers can receive safe conflicts. If a specific constraint/trigger prevents legitimate work, first pause the affected operation, capture the failure and verify owner data. Restore only the original trigger/function definitions captured by phase2-preflight-readonly.sql. Drop only the release-added named constraint/index after review, never CASCADE or delete rows. Index/constraint names are in phase2-watchlist-integrity.sql; parent uniqueness may have dependencies, so reverse dependency order if a separately approved rollback requires removal.

E01 rollback must use exact captured ACLs/proconfig/function EXECUTE grants for touched objects. Never GRANT ALL, restore unsafe PUBLIC access by guess, or replace RLS. Column ACLs/role membership can affect effective privileges; compare them first. Reinstating administrative browser privileges creates a security regression and requires explicit approval. Prefer a narrow legitimate DML/EXECUTE fix rather than restoring excess admin grants. Function bodies/search paths are restored from captured definitions, not from an assumed historical migration.

Hosted-intent metadata is additive and nullable. Keep columns and order history during application rollback. Do not erase unknown initialization attempts, provider references, receipts or subscriptions. Disabling the intent flag with old hosted clients can create a fresh reference for a new request: pause the hosted initialization route while reconciling outstanding references before any flag rollback. Native checkout and verified fulfillment stay available under their existing controls. Reconcile by existing verify/provider read APIs; never retry an uncertain initialization POST automatically or reverse a payment as a deployment test.

No numeric database types or existing values changed, so there is no numeric data rollback. Client intent memory and retained uploaded-media behavior are not migration receipts; preserve possibly referenced media. No automatic deletion/cleanup accompanies rollback.

A failed SQL transaction leaves its changes uncommitted. Capture exact error, stop and investigate; do not bypass timeout/validation checks. The isolated fixture tests the migrations twice and refused conflict state, but not a full production restore. A staged full-schema rehearsal and captured inverse ACL/function changes are release gates. No production rollback has been executed or needed for Phase 1.
